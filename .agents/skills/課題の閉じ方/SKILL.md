**アーキテクチャ課題は「解決」「受容」「退ける」で閉じる。受容と退けるを混ぜない。**
完成は「受容を除く未解決がゼロ、かつ要再確認の仕分け待ちがゼロ」で判定する。

## なぜこの体系で要るか

設計は矛盾と未確認を抱えて進むので、課題は出続ける。閉じ方を区別しないと、**「放置した」と「既知のリスクとして受けた」が同じ見た目になる。**
受容は「問題はあるが引き受ける」、退けるは「問題ではない」。混ぜるとリスクリストに誤った検出が並び、本当のリスクが埋もれる（§16.3）。
終わりの条件が無いと、決断のループ（課題の検出 → アプローチ → 案 → スナップショット → レビュー → 新たな構造 → 課題の検出）は止まらない。

- **解決**：決断で課題が無くなった。新しい構造が新しい課題を呼ぶ
- **受容**：未解決のまま既知のリスクとして受け入れる。リスクリストとディスクリプションに載せる
- **退ける**：判断で課題ではないとする（例：本質的な矛盾の候補を調べたら、案ごとに関心事の組が違っていた → 欠点の由来）。退けたときの検出の中身を控え、中身が変われば開き直す

> ⚠ 食い違い（師匠に確認）：§16.3 は 3 つに加えて「このほか**保留**もある。保留には再開の条件を書く（条件の無い保留は永久に保留のまま）」と書く。手法の用語集（12-glossary）の状態は 解決／受容／退けた の 3 つだけで、保留を持たない。

## How to apply

- **課題ごとに閉じ方を記録し、理由を添える。** 受容は誰が・何のリスクを・どの条件で受けたかの記録を指す（→ 確定の根拠）
- **退けた課題には「何が変われば開き直すか」を書く**
- **保留にするなら再開条件を必ず書く**（→ 解除条件の書き方）。保留は閉じ方ではない
- **課題は優先度順に解く。** 優先度 ＝ 届くドライバーの重み × 影響範囲（MD-016、→ 重みのラベル付け）
- **終わりを「完成度」の感覚で判定しない。** 受容以外の未解決の件数と、要再確認の仕分け待ちの件数で判定する（→ 上流変更の仕分け）
- ⚠ **「いったん完成」であって永遠ではない。** 実装先に割り付けると新しい課題が出て二週目が始まる（→ 割り付けの課題化）。範囲の目安は → 上位二割の検討
