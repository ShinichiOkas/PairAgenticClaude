**構造制約は「後から守られたかを検査できる形」で書く。**
検査できない制約は、方針であって制約ではない。

## なぜこの体系で要るか

`アーキテクチャ` の事後条件が「制約が後から検査できる形で書かれている」を要求する。
**構築者は設計書とコードを書くが、制約に違反したかを自分では判定しない。**

## How to apply

- **跨いではならない依存を、名前で書く**（「層 A は層 C を参照しない」）
- **検査手段を併記する。** import グラフ / ディレクトリ規約 / 実行時の境界
- **例外を書くなら、例外の条件と期限を書く**
- ⚠ **「〜すべきである」は制約ではない。** 違反を判定できる述語にする

## 足した具体（2026-10-27・AIdedArchitecture から抽出・未実走）

- **検査手段の例**: 対応規則（ダイナミックなモデルに出る要素・関連は、スタティックなモデルに必ずある）と、どこにも割り付けられていない要素の数（part2_道具編.md §5.6、AI ドラフト NT-60。→ 動的に見つけ静的に解く、→ 割り付けの課題化）
- **外に出したものは、変えられない制約として受ける。** 電源（家庭のコンセント）をシステムの外にしたので、使える電力の上限が制約になる（part3_実践編.md §11.5、NT-60）。変えてはならないプラットフォームの構造も同じ（§17 素材メモ）
- **決断の制約は must／must_not で書く。**「must 吹きこぼれを理由に沸騰を弱めない」は、却下した案を後から善意で足されることを防ぐ（§15.5、NT-60。→ 決断の禁止事項）
- **制約の無い決断は検出する。** 決まった案に must が無ければ「制約の無い決断」（part4_成果物編.md §21.4 注記、docs/method/14-textbook-correspondence.md W5。→ バックトレース）
