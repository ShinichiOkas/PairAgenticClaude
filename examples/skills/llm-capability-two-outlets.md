LLM にツールを使わせるには、**独立した2つの出口**を通る。

| 出口 | 実装 | 意味 |
|---|---|---|
| **渡す** | 有効ツール解決 → `llm.chat(tools=...)` | ツール定義を API に渡す |
| **見せる** | システムプロンプト構築 → ツール一覧のレンダリング | 「## 利用可能なツール」に列挙する |

**ツールの可視性を変えたら、必ず両方の出口を数える。**

**Why:** 「モード選択と無関係に LLM へ提示する」設計で条件付き注入の仕組みを作ったが、それは**渡す側だけ**だった。見せる側は通常の解決経路からしか生成されないため、既定モードの新規セッションではプロンプトの一覧に該当ツールが**一行も載らなかった**。

LLM は一覧に無いツールを避け、「その機能は利用できません」と答える。結果、**自動発動・スケジュール実行の経路で機能が実行不能**になっていた。

**この不整合は例外にもログにも出ない。** ツールは渡っているので API はエラーを返さず、LLM が「使わない」という応答を返すだけ。1年以上「動いていることになっていた」。

**How to apply:**

- ツールを条件付きで公開する仕組みを足したら、**一覧レンダリングまで届くか**を確認する。通常の解決経路を通らない注入（スキル定義・フックの追加ツール・外部エージェント・スラッシュコマンド）は**見せる側に自動では現れない**
- 解決を**単一点**に置き、両方の出口がそこから配られる形にする。片方の経路にだけ足すのではなく、一度だけ解決して同じものを両方へ渡す
- **フィルタの適用順**に注意する。注入がフィルタの後段だと、注入経由でフィルタを貫通できてしまう（プライベート遮断の抜け穴になった実例あり）。単一点に寄せるとフィルタも1箇所で効く
- **「渡す」だけを検証するテストは緑のまま通る。プロンプト本文を assert するテストを置く**
