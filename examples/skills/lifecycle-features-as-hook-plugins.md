「処理のライフサイクル（1ターン／1リクエストの前後）に絡む新機能」を追加するときは、**まずフックプラグインとして実装できないか検討する**。

**構成要素（5点セット）:**

1. `_FEATURE = "<name>"` 定数で feature 名を定義する
2. コンテキストへの注入は**前段フック**（`on_before_*`）、状態更新は**後段フック**（`on_after_*`）の背景タスクで行う（主処理のストリーミングをブロックしない）
3. 専用ストア（先行実装と同型の I/O）+ パス定義を追加する
4. feature gate は**フック側で自前確認**する。前段フック発火時点ではコンテキストの設定が未解決なことがある
5. エントリポイントで登録関数を**1行**呼ぶ

**Why:** コアの主処理を一切改変せずに機能を足せる。feature OFF 時はフックが発火せず**完全に無コスト・無干渉**になり、実験的機能の取り外しやすさが最大化する。

副次的な利点として、**制御下にないバックエンド（外部 LLM 等）に構造化出力を強制しなくて済む**。後段フックの背景呼び出しで応答テキストから事後抽出すれば、ディスパッチャや有効ツール集合を触らずに実現できる。

**How to apply:**

- 新機能の設計前に「**同型の先行実装があるか**」をまず探し、テンプレートとして精読する。2例目からは定型に乗せる
- 単位ごとの ON/OFF は既存の feature 設定＋UI トグルがそのまま使えることが多い。新規 UI はラベル1行で済む
- **射程を混同しない**: 1ターンに閉じた処理はフック、横断・アイドル駆動の永続化は別の仕組み（バッチ／コンソリデーション）の射程
