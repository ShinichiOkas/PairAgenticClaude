---
name: コード評価はテスト通過で行う
description: コード生成・修正タスクの評価は、事前に用意したテストケースの pass/fail のみで行う
type: feedback
---

コード生成・修正系のタスクを採点する評価設計を組むとき、判定軸は「事前に用意したテストケースが通るかどうか」のみとする。コードの構造、行数、複雑度、重複度、命名、可読性などの静的指標を評価軸に入れない。

**Why:** 「コード自体に振れ幅があったとしても、そのコードが事前に用意したテストケースを通ることで見れば一律に評価できる」。コード生成は本質的に揺れる。揺れに強い唯一の判定軸は「動くかどうか」。

**How to apply:**
- 評価設計を組むときは、まず「テストで判定できるか？」を考える
- 静的指標（重複削減率、行数、Lint 結果、複雑度など）を採点に組み込みたくなったら、まず「テストに置き換えられないか？」と問い直す
- リファクタリングのような「機能を変えずに構造を変える」課題でも、評価は「既存テスト全 pass」のみで行う。極端な話、AIエージェントが何も変えなくてもテストが通れば pass とする。それを「課題未達」と判定したいなら、追加のテストを書いて差を可視化する
- read-only 質問（コード理解・要約）も可能な限り「AIエージェントの回答を機械可読な形式で書き出させる → それをテストで検証」という形に揃える
- 主観評価・コードレビュー的な判定は採用しない
