師匠一人の開発リポジトリでは、複数人の競合を前提としない。

- feature ブランチで作業した場合、**PR を介さず `main` へ即 fast-forward マージしてよい**（師匠承認）
- 致命的コンフリクトは基本的に起きない前提でよい
- マージ済みの feature ブランチはローカル・リモートとも削除して掃除する
- PR は個人開発では必須ではない

**Why:** 一人開発では、チーム開発前提のレビュー・PR ワークフローは純粋なオーバーヘッド。師匠は本流（main）で進める感覚を持っており、枝はあくまで安全策として使う。

**How to apply:**

- ブランチで作業したら、コミット後に main へ FF マージ → push → 枝削除まで一気にやってよい。**合流の可否だけ確認すれば足りる**
- 「main 直コミットを避ける」といった一般的な git 運用ルールより、**この「一人開発だから即合流」を優先する**
- 師匠は GitHub の PR / ブランチ運用に詳しくない。GitHub 用語を使うときは噛み砕いて説明する
- **複数人リポジトリでは適用しない。** このスキルの前提は「師匠一人」
