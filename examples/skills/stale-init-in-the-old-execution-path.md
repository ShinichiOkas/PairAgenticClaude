機能を別の実行経路へ移したら、**両方向**を洗う。

1. **置き去りの初期化** — 旧経路のエントリポイント（`main()` / `if __name__ == "__main__"`）にしか無い初期化は、新経路では**一度も実行されない**
2. **到達不能な残骸** — 旧経路向けの probe・分岐・既読集合は、移設後も動き続けて**誤ったログと誤った前提**を残す

## Why — 同型の穴が2件同時に出た

**(1) 置き去りの初期化: 2ヶ月間まったく動いていなかった**

```python
_allowed_dirs: list[Path] = []

def main() -> None:                        # ← stdio 起動専用の入口
    global _allowed_dirs
    _allowed_dirs = _load_allowed_dirs()   # ← ここでしか代入されない
    mcp.run("stdio")
```

in-process transport へ移行し、呼び出し側は `import_module(...)` でオブジェクトを直接使うようになった。`main()` は**一度も呼ばれない**。`_allowed_dirs` は `[]` のまま、全ツールが「設定されていません」を返し続けた。**環境変数は正しく届いていた —— 読むコードが呼ばれていなかっただけ。**

**(2) 到達不能な残骸: 切り分けを遅らせた**

ある機能は独立サービスへ移設済みなのに、起動処理が存在しない旧ツール名を毎起動叩き続けた。`... not found in any connected server` という警告が「そのサーバーがまだその機能を扱っている」という**誤った前提**を残し、別件の切り分けを実際に遅らせた。関連する分岐・状態も到達不能なまま残っていた。

## How to apply

- **旧エントリポイントの中身を読む。** `main()` に初期化・グローバル代入・設定ロードがあれば、新経路は通らない。**transport 非依存の場所（初回参照時に解決するアクセサ）へ移す**
- モジュールレベルの即時実行にすると import 順に依存する。環境変数のエクスポートより先に import される経路が生まれると同じ穴に落ちるので、**参照時解決が安全**
- **旧経路向けのコードを名前で grep する**（旧ツール名・旧サーバー名・旧 URI）。残骸は「動かない」だけでなく**誤診を生む**ので削除する
- 残骸のテストは緑のまま残りがち。**存在しない名前をモックしたテストは本番経路を検証していない**。実在する名前へ移す
- **起動ログが「設定を読んだ」ではなく「実際にロードした結果」を出しているか確認する。** 「設定完了（dirs=...）」は環境変数を復唱していただけで、サーバー側が空だったことを隠していた
