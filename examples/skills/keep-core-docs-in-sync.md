**進捗ドキュメント（LONGTERM_TODO 等）／構造ドキュメント（PROJECT_STRUCTURE 等）／README** の3ファイルはプロジェクトの「顔」であり、構造把握・進捗管理の単一の入口。実装は速く動くのに、このドキュメントは手で追随させないと必ず陳腐化する。**放置しない。**

## WHEN — いつ更新するか

**必ず更新（大きな変更）:**

- ソースツリーに新規モジュール／ファイルを追加・削除・移動した
- 公開されるツール・コマンドを追加・削除した（数と分類が変わる）
- 新しいサブシステム／フェーズが動き出した／完了した
- 永続化・スキーマ・保存レイアウトを変えた
- ポート・設定キー・起動時配線（middleware / トークン / 自動接続）を変えた
- スプリント完了・マイルストーン到達・フェーズの %／ステータスが動いた

**定期的に（大きな変更が無くても）:**

- コミット時・振り返り時に「3ファイルの更新日は今日か？現在地の記述は最新か？」を一瞥する

## よく陳腐化する箇所

**進捗ドキュメント（進捗の正）**
- ヘッダの更新日
- **ヘッダの「現在地」行と各セクション見出しの %／ステータスの食い違い**（最頻出。サブ項目が全部 100% なのに現在地行が途中スナップショットのまま）
- クローズしたフェーズの「残: …」列挙から除外したか
- **フェーズ番号の重複**
- 「最新」を騙る数字（テスト数等）の陳腐化。履歴的スナップショットは残してよいが、現在地行は最新へ
- 実装済みなのに WBS 項目が無いサブシステムは1行足す（追跡漏れ防止）

**構造ドキュメント（構造の正）**
- ヘッダの最終更新日
- 各表と**実在ファイルの過不足**（新規は追加、削除済みは消す）
- トップレベルパッケージ・サブアプリ・vendor
- 公開ツール数と分類表
- 実行時データディレクトリのツリー（起動時に作られるディレクトリ・実ファイル）
- 起動時配線（新しい middleware・トークン・自動接続・サービス登録）

**README（利用者向けの顔）**
- 「◯種類以上の〜」といった数字の実数
- **バッククォート付きの名前がすべて実在するか**。「まとめ呼称の幻の名前」を書かない。実名を列挙する
- リファレンス表の出典を明記し、その出典と一字一句一致させる
- 大きな新機能はトップの「主な機能」にブロックを足す。表の中にしか出てこない機能を放置しない

## HOW — 実行手順

1. **実装の実体を取る（推測しない）**: ソースツリーの実ファイル一覧、公開ツールの実名と数、保存レイアウトの生成コード、スキーマバージョン、直近の git log、最新のフルスイート結果
2. 上記「よく陳腐化する箇所」に沿って突き合わせ、ADD / REMOVE / FIX を洗い出す。規模が大きければ3ファイルを別々の調査エージェントに投げて乖離リストを作らせると速い
3. **差分だけを Edit で当てる**（全書き換えはしない。既存の良い構造は残す）
4. 3ファイルとも更新日を今日へ
5. **検算**: 直した箇所が本当に実装と一致するか（特に名前は出典と一字一句）
6. 更新内容を師匠へ要約報告する（勝手に完了扱いにしない）

**Why:** 師匠の明示指示 —— 「この3ファイルは重要なので定期的に更新、大きな変更があった際は必ず更新するスキルを作っておいて」。点検時には一連の作業に対して3ファイルとも乖離しており、「現在地行が途中経過」「新サブシステム丸ごと未記載」「実在しないツール名」「構造変更後の保存レイアウトが旧のまま」が同時に積み上がっていた。**「動いているのに書かれていない」機能が溜まると、ドキュメント起点の調査という前提そのものが裏切られる。**

**How to apply:**

- 大きめの実装スプリントの**完了条件**に「3ファイル同期」を含める（コミット前チェック）
- 構造重複を潰す系の変更は「消したファイル／増えたファイル」を構造ドキュメントの表に必ず反映する
- 迷ったら全書き換えではなく差分 Edit。履歴的スナップショット（過去のテスト数など）は消さない
