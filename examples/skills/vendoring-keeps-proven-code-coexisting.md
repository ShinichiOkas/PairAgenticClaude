外部コードをベンダリング（`_upstream/` 等へ取り込み）して既存実装を置き換えるとき、**既存コードを削除せず共存させる**。

1. 取り込んだコードは「削除候補」ではなく独立した外部依存として置く
2. 既存の同等モジュールは**当面残す**。公開関数として存置し、必要なら直接使える状態を保つ
3. アダプタが上流を呼ぶように書き換えても、既存関数の存在自体は維持する
4. **死活コード整理（削除可否の判断）は、取り込み完了後の別スプリント**で改めて検討する

**削除する / 残すの境界:**

- **削除する** — 機能的に上流関数で**完全に置き換わった**もの（依存ライブラリごと切り替わった等）
- **残す** — 上流に同等関数があるが、**既存側が実機検証済みで動作している**もの

判定基準: **「上流に切り替えると壊れる可能性がゼロでないなら残す」**。

**Why:** 師匠の明示宣言（「当面共存だな」）。既存コードは実機検証済みで、上流に切り替えた直後にバグが出てもフォールバックできる構造が安心。上流が将来大きく変わったときのロールバック余地も残る。**「動いてるコードを触らない」**が原則。

実際、取り込み完了後の判断は「アダプタ全面スワップは**やらない**（動作実証済みのコードを書き換える価値が薄い）」「死活コード整理は必要になったタイミングで」に落ち着いた。共存させておいたことで、後から冷静に「やる価値 vs 壊すリスク」で判断できた。

**How to apply:**

- 取り込み計画の時点で「共存」を明示的に選ぶ。削除を後続タスクとして WBS に立て、同じスプリントに混ぜない
- 共存させたコードは一覧化して引き継ぐ（どのファイルが「完全維持」「アダプタ化」「削除済み」「取り込まない」か）
- 「掃除したい」という動機だけで削除しない。削除の理由は「呼ばれていないことを確認した」であるべき
