git submodule ではなく**直コピー**で取り込んだ vendor ディレクトリは、時間が経つと**双方向に**乖離する。

| 方向 | 溜まるもの |
|---|---|
| **vendor のみ** | この製品で踏んだバグの修正・この製品向けの挙動変更 |
| **本家のみ** | リネーム・API の public 化・関数削除・新機能 |

**本家からの単純コピーは退行になる。** 再取り込みは「**vendor 側にしか無い修正を先に本家へ移植 → そのうえで取り込み**」の順で行う。

**Why:** vendor 側の修正を本家へ移植する過程で判明した。本家に修正が無いことに加えて、**本家に無い vendor 側修正**まで見つかった。

同じバグでも壊れ方が両者で違っていた。古い vendor は内部構造がそのまま画面に出る＝**見えて気づける**壊れ方、新しい本家は黙って本文を切る＝**もっともらしい途中終了・警告なし**。**古かったおかげで気づけた**、という皮肉な状況だった。

供給元の確認も要る。本家リポジトリがローカルにしかなく、公開リモートより大幅に先行していることがある（push が禁止設定になっている等）。**公開リモートから取ると大幅に古い**。

**How to apply:**

- vendor ディレクトリを触る前に、本家の同ファイルと diff を取る
- vendor 側に修正を入れたら、**同じ修正を本家へも移植する**。片方だけに入れると乖離が増える
- 再取り込みの作業計画は WBS に立て、「vendor → 本家の移植」を**先行タスク**にする
- 呼び出し側が本家の private 名を import している場合、取り込み時に呼び出し面の読み替えが要る。これも計画に含める
- 「本家を先に確認する」を習慣にする。ワークアラウンドを書く前に、本家に既に直っていないかを見る
