自律系（LLM エージェントのループ）が遅いとき、**速度の最適化を始める前に正しさの欠陥を
修理する**。実行時間の大半は本来の作業ではなく、**病理の間接コスト**——理解できない
エラーへのリトライ、規範が届かないことによる試行錯誤、壊れた検査に落とされてのやり直し、
矛盾した要求との整合作業——である可能性が高い。

**Why:** ある自律系の製品での実測（2026-08-07〜08）。同一課題・同一モデルの6走で、走行時間は
25〜51分 → **4分15秒**になった。速度を目的にした変更は**一度もしていない**。
消えたのは全て正しさの病理の間接コスト:

| 病理 | 間接コスト |
|---|---|
| BOM なし .ps1 を 5.1 が CP932 と読む | ParserError の書き直しループ 6〜8分 |
| 規範が下位のエージェントに届かない | 判定書の形式試行錯誤 10〜40分 |
| 下位の壊れた自作検査 | 正しい判定書の書き直し ×3 |
| 捏造マーカー（答えの仮定） | 矛盾する要求との整合作業・偽データ生成 |
| QA の write_scope 衝突 | 権限拒否 33回の空転（過去走） |

病理ゼロの走行に残ったのは素の作業時間（設計→実装→実行→検証）だけだった。

2例目（2026-08-10・領域を跨いで再現）: 非コーディング領域（ディープリサーチ）の同一課題で
約65分（偽 ACHIEVED で終了）→ **2分11秒（本物の達成）**。ここでもコード変更はゼロ
（修理群の横展開のみ）。当時の65分の内訳は検査器の書き換え合戦・QA の権限拒否33回・
マーカー不一致の整合作業だった。

**How to apply:**

- 「遅い」という観測に対して、まず**時間の内訳**を取る: 本来の作業 vs リトライ・
  やり直し・試行錯誤。後者が優勢なら、それは速度の問題ではなく正しさの問題
- リトライループの中身を読む（ログの実物）。同じエラーの繰り返しは高速化の対象ではなく
  修理の対象
- 並列化・キャッシュ・モデル変更などの速度施策は、病理の間接コストを**温存したまま
  隠す**ことがある（速く失敗を繰り返すだけ）。順序は正しさ→速度
- 人間の組織と同型: 手戻りだらけの工程を人員追加で速くしない
