新しい能力（ツール・プロバイダー・アクション）を足すときは、**登録点を数えて潰す**。実装ファイルを書いただけでは、どこにも公開されない。

## 数え方

1. **本体の登録点を列挙する** — 実装 / 定義テーブル / ディスパッチャ / 依存注入 / **モード集合・有効化集合** / カテゴリ分類 / 遮断リストの要否 / 設定キー・secrets・`.env.example`
2. **本体外を grep で洗い出す** — `grep -rn "provider ==" ` のように**分岐そのものを名前で検索**する。本体の switch を独自に複製した箇所がスクリプト・テスト・サブアプリに潜んでいる
3. **実経路で到達可能になったことを確認する** — 単体テストは実装関数を直接呼ぶので、**公開漏れを検出できない**

## この一覧を信じて grep を省かない

**一覧は書いた時点の写真**であり、次に複製が増えたときは更新されていない。既存のチェックリストドキュメントは、廃止済みの手順を載せたまま新しい登録点が丸ごと欠落していることがある。**チェックリストに従っていたら漏らしていた**、という実例が出た。**参照する前に現行コードと突き合わせる。**

## 複製を見つけたら「分岐を足す」より先に「寄せられるか」を見る

複製された switch に分岐を1つ足すのが正しいのは、**その複製が本体と同じ広さを持っているとき**だけ。実際に見た内訳は、本体が6分岐なのに複製は2〜4分岐で、しかも `else` が**未知を黙って既定へフォールバック**していた。

ここに1つ足しても**残り3〜4は壊れたまま残る**。分岐追加は「今回の分だけ直る」対症で、複製を消す方が変更行数も小さかった。

判断の順序:

1. その複製は本体と同じ広さを持っているか → **grep で数える**（「動いているから合っている」で済ませない）
2. 遅れているなら単一の生成点へ寄せる
3. 寄せられない理由がある場所だけ分岐を足し、**なぜ寄せないのかをコメントか記録に残す**

**Why:** 同じ病理が繰り返し出た。**実装は在るのに、外へ見せる／実行させる配線が1点欠けていて、しかもテストもログも異常を示さない。** 「実装完了・全テスト green」と記録された機能が、実際には LLM から不可視で一度も呼ばれていなかった。フルスイート green は**到達可能性を保証しない**。

未知を既定へフォールバックする複製の `else` は、さらに悪い壊れ方を生む。「新プロバイダーの API キーを持った別プロバイダーのクライアント」が生まれ、起動はするが認証エラーで死ぬ。

**How to apply:**

- 能力追加タスクの**完了条件**に「`grep` を打って全ヒットを処理」「実経路での到達確認」を含める
- レビュー時は定義ファイルの diff を見たら、**必ず登録ファイルの diff も探す**
- **寄せた副作用を必ず確認する。** 「switch が知らない → None → *たまたま* skip」で守られていたテストは、寄せた瞬間に実際に API を呼びに行くようになる。**skip の理由が「知らないから」だった箇所は、寄せると意味が変わる**
- 設定値に**推測値を置かない**。公表値が無いものは登録せず未設定のままにする。ただし「公表値が無い」と決める前に、別エンドポイントに無いかを見る
