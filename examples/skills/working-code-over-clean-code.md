---
name: 動くコード ＞＞ きれいなコード
description: 動くコードを最優先する。コードの美しさ・構造的洗練・命名の議論で実装判断を縛らない
type: feedback
---

設計判断の岐路では「動くか・テストが通るか」を最優先する。コードの美しさ、構造的洗練、命名の議論、行数、複雑度などの「きれいさ」軸は、動くという前提が満たされた上で初めて検討できる二次的指標であり、それ単体で実装方針を縛ってはならない。

**Why:** 「動くコード＜＜きれいなコード」という思想が重要。これは上位思想であり、既存 Skill `eval-by-tests-only.md`（コード評価はテスト通過で行う）の親概念。

**How to apply:**

- 評価設計・採点設計を起こすときは、最初に「動いているか／テストが通っているか」だけで合否を決められる形を考える。静的指標を持ち出したくなったら一段下がる
- リファクタ系のタスクでも「リファクタしたか」を判定軸に入れない。「既存テストが pass しているか」だけで判定する
- 提案や設計レビューで「もっときれいに書ける」「冗長」「重複している」を理由にした書き換えを推奨しない（明示的に求められた場合を除く）
- AI 自身のコードレビュー基準も同じく「動くか／テストが通るか」を最優先する
- 既存 Skill `eval-by-tests-only.md` はこの思想の一応用と位置づけて参照する
