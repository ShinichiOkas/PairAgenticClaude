会話履歴を別形式へ正規化・変換する層（プロキシの互換フロントエンド等）を書くとき、**どこまで厳密に合わせるかは、最終的にそれを消費するレンダラの契約を先に読んで決める**。

実例: テキスト補完型のバックエンドへ中継するプロキシでは、ツール呼び出しブロックが最終的に

- `tool_use` → `<tool name="{name}">{input_json}</tool>`
- `tool_result` → `<result>{content}</result>`

のようなテキストタグに描画され、`tool_use_id` / `tool_call_id` は**どこにも出力されない**。この場合、OpenAI/Ollama 形式の履歴（assistant の `tool_calls` と `role:"tool"` 結果）を Anthropic 形ブロックへ戻すとき、**id の厳密な突き合わせは不要**で、ブロックの**順序と中身**（name/input、result content）さえ正しければモデルは正しく解釈する。tool_call に id を持たないクライアントも、id を合成・補完せずそのまま扱える。

**Why:** マルチターン正規化に id の対応管理が必要かを調べたところ、最終レンダラが id を無視すると判明し、正規化を「順序と中身だけ」に単純化できた。レンダラの契約を読まずに設計していれば、使われない id 対応表を作り込んでいた。

**How to apply:**
- 履歴・データの正規化層を設計する前に、**変換先で実際にどう描画・消費されるか**（どのフィールドが使われ、どれが捨てられるか）をコードで確認する
- 捨てられるフィールドの整合性管理は作り込まない。登場順どおりに並べるだけで足りるならそうする
- ただしこの単純化は「レンダラが id を使わない」という前提に依存する。**前提をスキルや設計メモに明記し、レンダラが構造化入力を受けるようになったら見直す**
