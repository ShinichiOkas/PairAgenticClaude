**品質要求は、シーケンス図の「区間」（始点メッセージ〜終点メッセージ）に測定値と目標値を付けて書く。六要素が図の上で決まる。Source を省かない。**
品質要求を別の文書に書くと、ユースケースと食い違い、要素が黙って欠ける。

## なぜこの体系で要るか

品質特性シナリオ（→ 品質特性の操作化）は文章で書くと要素が欠けやすい。区間に付けると対応が機械的に決まる（§14.7）:
Source＝始点メッセージの送り手／Stimulus＝始点メッセージ／Environment＝図の切り取り条件（事前状態を含む）／Artifact＝システム／Response＝終点メッセージ／Response measure＝区間の測定値と目標値。

**失敗例**: 「処理中も操作できる」の Source を書かなかったため、利用者の操作に伴う処理だけを指すつもりが、あらゆる処理に当てはめて読まれ、存在しない矛盾が作られた（G17）。
**例（炊飯器）**: 「炊飯を始める」（利用者→炊飯器）〜「炊き上がりを知らせる」（炊飯器→利用者）に「白米 3 合・水温 20℃・室温 20℃」「60 分以内」（数値は仮説）。

## How to apply

- **品質要求を区間に紐づけて書く。** 別文書にしない
- **六要素の空欄を「仕様欠落」として扱う。** 特に Source（誰の操作に伴う処理か）
- **Environment は SEI の意味（シナリオの実行条件）で使う。** 42010 の environment（システムを取り巻く文脈）とは別
- **同じ区間に別の関心事の目標を並べてよい**（1 回の電力量、吹きこぼれ 0 件）。内側への配分は → 区間目標の予算配分
- ⚠ 食い違い（師匠に確認）: 教科書 §14.4 は「Response と Response measure、場合により Environment を特定すれば十分」（他はユースケースシナリオで導出済みのため）。手法は区間から六要素すべてを決め、欠けを検出する（MD-039・T8）
