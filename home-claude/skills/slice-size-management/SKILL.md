# スライスサイズ管理プロセス (slice-size-xs-s-m-l-omakase)

**成熟度: confirmed（師匠の明示宣言 2026-09-15）**

> **「S,M,Lはサイズ？わかりやすくていいかもね。じゃあそれ採用しましょう。夜は夜とは限らないので『おまかせ』にしましょう。『この案件をMでおまかせで』というのがよさそう。ただ、議論してみて初めて大きいことが分かったり、実装の途中で前提がずれていて大きくなる等の変化をするのである程度動的のほうが良いと思う」**（師匠の言葉・2026-09-15）

## 1. サイズの定義と編成

親（主エージェント）はスプリント開始時に合意ドキュメント（またはバグ票）へ「スライス: ○（おまかせ）」を 1 行記載する。

| サイズ | 意味 | 走らせるエージェント編成 | コスト・所要時間 |
|---|---|---|---|
| **インライン** | 1 コンテキスト。役割定義を親が自らのチェックリストとして当てる | 親だけ | 最安 |
| **XS** | 親が実装し、受入検査実施者（＋非回帰）だけ別コンテキストに分ける | 受入検査実施者（＋非回帰） | 極小（「空の一時環境で確認」の偽陽性を防ぐ） |
| **S** | バグ票が仕様。単一機能修正 | 構築者 → 非回帰 → 受入検査実施者 → 同期担当 | 小 |
| **M** | 合意ドキュメントを書く標準的な機能スプリント | 意図取得 → 仕様 → 受入検査設計・構築 → 非回帰・受入検査 → 報告・同期 | 中 |
| **L** | アーキテクチャ、外部依存、基盤・保存先が動く大規模スプリント | M ＋ 探針複数 ＋ 詳細設計 ＋ 配布追従検査 | 大 |
| **おまかせ** | 判断ポイントを事前に細かく問わず、AIの推奨案で自律進行し、判断一覧を事後報告にまとめる | どのサイズにも付加可能。親はモデルを下げてよい | 自律高速 |

## 2. サイズの動的変更ルール

サイズは固定ではなく、途中で動かしてよい。
合意ドキュメントの「スライス」行を上書きせず、**「S → M（日付・理由）」** と追記する。

### サイズを上げる判断点:
1. 協議で論点が収束しない・前提崩壊が発覚した
2. 探針（probe）で技術的制約が見つかった
3. 差し戻しが発生した
4. いずれかの役から「範囲外（スコープ外）」が上がった
5. 変更対象が 3 ファイルを超える、または新モジュール作成を伴う
※ 「おまかせ」指定時は主エージェントが自律的にサイズを引き上げて事後報告。通常時は 1 行で師匠に伺う。

### サイズを下げる判断点:
- 「まだ走っていない役を省く」場合のみ下げる。
- 既に走った役の成果物は破棄しない。
- 親が遮断対象を読んだ後に、その役を兼任してはならない（遮断の不可逆性）。

## 3. 「おまかせ」でも必ず停止・確認するもの
1. 人間ゲート（`gate: H1...`）の承認
2. GUI 目視確認などの官能検査
3. 破壊的操作（git push -f、DROP TABLE、大量ファイル削除など）
4. 外部への情報送信
5. 師匠が手動作成した成果物の上書き
