**結論を伝える文書と、結論の導出根拠を残す文書は、別の文書にする。互いを ID の参照で結ぶ。**
読み手はアーキテクト自身ではない。結論だけ読みたい読者のほうが多い。

## なぜこの体系で要るか

`アーキテクチャ` の読み手（仕様作成者・構築者）は、結論に従って作る。根拠を読むのは結論を疑うときだけである。
教科書は 2 文書に分ける（§19.1）：**ディスクリプション**＝採用した案だけで構成した結論（選ばれなかったアプローチは書かない §19.4）／**アプローチ**＝課題ごとの検討の経緯と決定に至る根拠。
**寿命が違う。** ディスクリプションは一つの対象物に対する結論の集合で寿命が短く、アプローチはほぼ永続する判例集になる（§19.5）。同じ文書に置くと、短い方に引きずられて長い方が捨てられる。
ISO/IEC/IEEE 42010 の architecture description は決断と根拠まで含むが、教科書は意図的に範囲を狭めている（MD-064）。

## How to apply

- **ディスクリプションの目次は結論が先、根拠は後**：目的／コンテキスト／ビュー／決断の一覧／関心事とドライバー／受容した課題・リスク／未決事項／用語（§19.6）
- **ディスクリプションに、選ばれなかった案を書かない。** 書きたくなったら、それはアプローチ側の内容である（却下案の保持は → 判例の照合）
- **決断の一覧の各行から、根拠のアプローチへ ID で辿れるようにする**
- **合意に使った版は、その時点で凍結して発行する。** 何に合意したかを後から辿れ、発行どうしを比べられる（§19.6）
- ⚠ **ディスクリプションを手で補わない。** 違っていたら元（モデル・アプローチ）を直す（→ 生成物の直し方）
