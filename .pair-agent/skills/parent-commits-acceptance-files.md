## ルール

- 受入検査仕様・受入検査報告書（`.pair-agent/acceptance/` 配下）は、**親が別コミットにして push する**
- 同期担当のブリーフには「`.pair-agent/acceptance/` は add しない（親が扱う）」と書く。対象に含めない
- 親のコミットは同期担当のコミットと**分ける**（`docs(<scope>): <sprint> の受入検査仕様と報告書` の形）
- **遮断のほうを外さない。** 同期担当が「deny-map のブロックを外せば add できる」と提案しても採らない ——
  遮断は「実装した本人が合格を出さない」を支える仕組みで、権限の変更はサブエージェントの提案で決めない

## Why

同期担当は受入検査の中身を読んではならない役（遮断: 受入検査仕様・報告書）で、フックは Read だけでなく
`git add` の対象指定でも止める。一方で受入検査ファイルは事故の証拠と合否の根拠で、コミットしないと
後から辿れない。親は既に受入検査の報告を検めている（遮断対象を読んでいる）ので、親がコミットしても
遮断は崩れない。

実際に 2 スプリント連続で同じ止まり方をした:

| スプリント | 何が残ったか | どう処理したか |
|---|---|---|
| continuation-directive-20260916 | 受入検査仕様・報告書（1 周目・2 周目）の 3 件 | 同期担当が add で遮断に当たり、deny-map を外す案を返した → 親は採らず師匠に仰ぐ → 親がコミット（`894c0c49`） |
| mcp-busy-server-20260917 | 受入検査報告書 2 件 | 最初から同期担当の対象外にした → 師匠の判断でルール化 |

## How to apply

- スプリントの同期段で、同期担当を起動する前に `.pair-agent/acceptance/<sprint>*` の有無を見る
- 同期担当が終わったら、親が `git add .pair-agent/acceptance/<sprint>*` → commit → push する（同期担当の push の後）
- `.pair-agent/assurance/`（設計保証）は同期担当の遮断対象ではないので、同期担当のコミットに含めてよい
