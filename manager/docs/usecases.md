# Pair Agent Manager — 利用者の作業から決める（動機・目的・きっかけ・基本フロー・例外フロー・人間の判断）

- 記録日: 2026-11-15
- 前の版（1 機能 1 タブの画面）は、依頼文の機能の列挙をそのまま画面にしたボトムアップ設計だった。師匠の指摘「ユーザーが作業する動機、目的、それに対する基本フロー、例外フロー、という形で検討していないからこうなる。やり直し」を受けて、ここから決め直す
- 判断は推奨で置いた。覆したいところだけ直す

## 0. 前提: ルールは「勝手に生まれて、勝手にずれる」

ルール・スキルは師匠が書くのではなく、エージェントが作業の中で書く（宣言の登録・叱責の記録・振り返り・プロジェクト固有の Skill）。
だから師匠は「いつ・どこで・何が増えたか」を知らない。実データ（2026-11-15・この PC）で、すでに次のことが起きている:

| 起きていること | 実例 | 害 |
|---|---|---|
| 配布先で新しいルールが生まれ、マスターに上がっていない | `~/.claude/CLAUDE.md` に「作る順序は UI ファースト（絶対ルール・2026-11-14）」の節が直接足されている。マスターに無い | 他の PC・他のユーザーのエージェントは、この絶対ルールを知らない |
| マスターで直したルールが、配布先に届いていない | マスターの `pair-agent-core.md` は「迷ったら project か archive に保存」に改めた（BUG-20261102-02）。この PC の `~/.claude/rules/` は古い「迷ったらペア固有側に保存する」のまま | **いま動いているエージェントが、直したはずの古い規則で動く** |
| 同じファイルの中で、上の 2 つが同時に起きている | `CLAUDE.md` と `pair-agent-core.md` は、どちらも「配布先が新しい部分」と「マスターが新しい部分」を両方持つ | ファイル単位で「上書き」も「取り込み」もできない |
| ペア固有層の同期が切れている | `~/.claude/pair-agent` は git 管理だが remote が無い。マスターの `external/pair-agent-skills` はこの PC では空 | ペア固有の 660 件が、他の PC と一切共有されていない |
| 古い写しがプロジェクトに残る | 実データの検査で、マスターの CLAUDE.md の節の古い写しを持つプロジェクトが複数見つかった（例: llmbenchmark） | そのプロジェクトのエージェントは古い規範で動く |
| 他人のリポジトリにも CLAUDE.md がある | 探索で、サードパーティのリポジトリ（CL4R1T4S・openclaw・opencode など）が候補に出た | 勝手に配ると他人のリポジトリを汚す |

## 1. 利用者と動機

利用者は師匠 1 人（後に他のユーザー）。何十ものプロジェクトと複数の PC で、Claude Code と Antigravity のエージェントと作業している。
**師匠はコーディング中、ルールの棚卸しに帯域を割けない**（CONCLUSION-20261102: 承認で昇格する設計は、誰も見ないので破綻した）。

| 動機（師匠が困ること） | 目的（こうなってほしい） |
|---|---|
| D1. ある場所で言ったことが、別のプロジェクト・別の PC のエージェントに効いていない | 師匠の宣言は、言った場所に関係なく全部のエージェントに効く |
| D2. 直したはずの規則で、エージェントがまだ動いている | 直した規則は、すぐ全部の配布先で効く |
| D3. エージェントが、ぶつかる 2 つの規則のどちらで動くか分からない | 同時に効く規則どうしがぶつからない。ぶつかるなら、状況で分けてどちらも正しくする |
| D4. プロジェクトの事情が全体のルールに漏れて、他のプロジェクトで変な振る舞いをする | 全体のルールには一般化したものだけが入る。固有のものはそのプロジェクトに留まる |
| D5. ルールが膨れて文脈を食う | 同じことを言う規則は 1 つにまとまる |

**師匠がやりたいことは「管理」ではない。「どこでも同じ、正しい規範でエージェントが動いている」状態を、手をかけずに保つことである。**

## 2. いつ動かすか — 常駐して、自動で点検する（推奨）

- **常駐する。** ログオンで起動し、タスクトレイに居る。GUI は普段は閉じている
- **点検は自動。** きっかけは 2 つ: (a) ルール・スキルのファイルが変わったとき（監視）、(b) 定期（既定 30 分）。`git pull` でマスターが変わったときも (a) に入る
- **手動の「今すぐ点検」も置く**（新しい PC で最初に使うとき・自分で直した直後）
- 却下した案: 手動トリガーだけ（師匠が開かない限り何も起きない＝今と同じで、ずれが溜まる）。Claude Code のフック（セッションの始めに走るフックは師匠が消した。応答を遅らせない）

## 3. 何が自動で、何が人間の判断か

**AI（ツール）が自動でやって、事後に報告するもの**（取り消せる）:

| 起きたこと | 自動でやること |
|---|---|
| マスターが新しく、配布先は最後に配った版のまま | 配布先へ配る（上書きの前に退避） |
| 配布先で新しいルールが生まれた（配布先だけが変わった） | 一般化できるか・どのスコープ（全体・ユーザー・プロジェクト）かを見立て、ぶつかる規則が無ければマスターへ取り込む → ほかへ配る |
| 双方で変わった（同じファイルの別の箇所） | 節ごとにマージする（配布先の新しい節はマスターへ、マスターの新しい節は配布先へ） |
| 全体のルールに固有名が漏れている | 一般化した案に置き換えるか、そのプロジェクトへ移す |
| 見つかったプロジェクトが `.pair-agent/` を持つ（Pair Agent を導入済み） | 管理下に入れる |

**人間（師匠）の判断だけが要るもの**（ここだけが師匠の作業のきっかけになる）:

| 判断 | なぜ人間か |
|---|---|
| J1. 同時に効く 2 つの規則がぶつかる: どちらを採るか・状況で分けるか・統合するか | 規範の価値判断。師匠にしか決められない |
| J2. 双方で同じ箇所が変わり、マージできない | 同上（J1 の一種） |
| J3. 見つかったリポジトリを管理に入れるか（`.pair-agent/` が無いもの） | 他人のリポジトリかもしれない。書き込む前に確かめる |
| J4. 他のユーザー由来のルールを、自分の規範に入れるか | 師匠の規範は師匠のもの |
| （事後）自動でやったことを取り消すか | 見て違っていれば戻す。見なくても回る |

## 4. 検査で真っ先に検出すべきこと

**「いま動いているエージェントが、正しい規範で動いていない」こと。** 優先度の順:

1. **同時に効く規則どうしの矛盾**（J1）。同時に効く＝同じエージェントが同時に読む集合（全体＋ユーザー＋そのプロジェクト）。
   別々のプロジェクトの規則がぶつかっても、同時には効かないので矛盾ではない（状況が違う）。検査はこの「効いている集合」の中だけで行う
2. **効いている規則が古い**（マスターで直したのに届いていない）。自動で配って直る。配れなかったときだけ上がる
3. **新しい宣言がマスターに上がっていない**（ほかに効いていない）。自動で取り込んで直る。ぶつかるときだけ J1 として上がる
4. **固有名の漏れ・冗長**。自動で直して事後報告

## 5. 師匠の作業のきっかけはどう上がってくるか

- 判断待ち（J1〜J4）が生まれたら、**Windows の通知**を 1 回出す（「判断待ち 1 件: 規則の矛盾 — 運転方針 × セッションの始め」）。押すと GUI がその項目で開く
- 判断待ちが無ければ、何も上がってこない。自動でやったことは GUI の「自動でやったこと」に溜まるだけ（通知しない）
- 判断待ちを放っておいても、エージェントは止まらない（今の規則のまま動く）。ただし J1 は効いている害があるので、最上段に出し続ける

## 6. ユースケース

### UC1. 判断待ちを片づける（人間の判断）

- 動機: エージェントがぶつかる規則で迷わないようにしたい（D3）
- きっかけ: 通知「判断待ち 1 件」
- 基本フロー:
  1. 通知を押す。GUI が判断待ちの項目で開く
  2. 1 枚のカードに、判断に要るものが全部ある: 何が起きたか／規則 A と B の本文（出所・日付・師匠の原文）／どこで同時に効くか／AI の見立て（矛盾か・状況次第で両方真か・提案する状況）
  3. 選ぶ: 「A を採る」「B を採る」「状況で分ける（AI の案を直せる）」「統合した文案にする（AI の案を直せる）」「あとで」
  4. ツールがマスターに反映し、全配布先へ配る。カードが消え、「自動でやったこと」に載る
- 例外フロー:
  - どの選択肢も違う → 一言で指示を書く → AI が文案にする → 3 に戻る
  - AI の見立てが無い（LLM が使えない: GPU 使用中・Ollama 停止）→ 本文と出所だけでカードを出し、見立ては「保留」と示す。使えるようになったら見立てを足す
  - 判断の後で配布先へ書けなかった（ロック・権限）→ 次の点検で再試行。3 回失敗したら判断待ちに戻す
  - 判断を間違えた → 「自動でやったこと」から取り消す（UC2）

### UC2. 自動でやったことを確かめ、必要なら取り消す（事後）

- 動機: 見ていないところで規範が変わるのが不安。違っていたら戻したい
- きっかけ: 師匠が気になったとき（通知はしない）
- 基本フロー: 時系列の一覧（いつ・何を・どこへ・なぜ）を見る → 差分を開く → 違っていれば「取り消す」→ 元の版に戻り、配布先にも戻す
- 例外フロー: 取り消そうとした版の後で、さらに変わっている → 取り消しは判断待ち（J2）になる

### UC3. 新しいプロジェクト・新しい PC で使い始める

- 動機: どこで作業しても同じ規範で動いてほしい（D1）
- きっかけ: 新しい PC に入れた／新しいプロジェクトを作った（常駐の点検が見つける）
- 基本フロー: 点検が新しいリポジトリを見つける → `.pair-agent/` があれば自動で管理下に入れて配る → 事後報告
- 例外フロー: `.pair-agent/` が無い（他人のリポジトリかもしれない）→ 判断待ち J3「管理に入れる／外す」。外したものは二度と聞かない

### UC4. ほかの PC・ほかのユーザーと揃える（GitHub）

- 動機: 別の PC で生まれたルールも、ここで効いてほしい（D1）
- きっかけ: 常駐の点検（マスターの `git pull` を含む）
- 基本フロー: 各 PC のツールが、取り込んだ変更をマスターに commit・push する → ほかの PC は pull して、UC1〜UC3 と同じ流れで配る
- 例外フロー: git の衝突 → 節ごとにマージ → 無理なら J2／ほかのユーザーの個人の規則 → J4

### UC5. 理由を調べる（任意・道具）

- 動機: 「なぜこのエージェントはこう動いたのか」を知りたい
- 基本フロー: プロジェクトを選ぶ → そのエージェントが読む規則の全部（効いている集合）を出所つきで見る → 差分・本文を開く
- 前の版の画面（配布状況・差分・サーベイ・検査・再配布）は、ここの「道具」として残す

## 7. 画面（ここから導く）

| 画面 | ユースケース | 普段 |
|---|---|---|
| 判断待ち | UC1・UC3 の J3・UC4 の J4 | 通知から開く。0 件なら「やることはありません」 |
| 自動でやったこと | UC2 | 気になったときに開く |
| 効いている規則 | UC5 | 調べるときだけ |
| 管理下（PC・プロジェクト） | UC3・UC4 | ほぼ見ない |
| 設定 | 常駐・点検の間隔・通知・LLM | 最初だけ |
| 道具（詳細） | 前の版の画面 | 調べるときだけ |

ヘッダに常駐の状態（最終点検・次の点検・「今すぐ点検」）を常に出す。

## 8. LLM の使いどころ（このフローから決まる）

| 場面 | 機械 | LLM | 出力の扱い |
|---|---|---|---|
| 規則の矛盾の検出（J1 の候補） | 効いている集合の中で、話題の近い組を絞る | ぶつかるか・状況次第で両方真か・提案する状況 | カードの「AI の見立て」。決めるのは師匠 |
| 判断の文案（状況で分ける・統合） | — | 文案 | 師匠が直して確定 |
| 新しい規則のスコープ判定・一般化 | 固有の語の検出と残りの検査 | スコープの見立て・一般化した文 | 自動で反映し、事後報告（取り消せる） |
| 節のマージ（J2 の手前） | 節に切る・どちらが変わったかを台帳で判定 | 同じ節が両方で変わったときの合成案 | 合成できなければ J2 |

モデルの既定は `gemma4:31b-cloud`（GPU を使わない）。LLM が使えないときは、機械でできる点検だけを続け、LLM の要る見立ては保留にする。
